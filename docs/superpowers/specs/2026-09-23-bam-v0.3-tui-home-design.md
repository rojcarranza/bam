# bam v0.3: terminal UI home table

**Status:** Implemented | **Date:** 2026-09-23
**Product requirements:** [`docs/prd.md`](../../prd.md) §7
**Builds on:** [`2026-09-18-bam-v0.2-tui-navigate-design.md`](2026-09-18-bam-v0.2-tui-navigate-design.md) (part A) and [`2026-09-18-bam-v0.2-tui-actions-design.md`](2026-09-18-bam-v0.2-tui-actions-design.md) (part B). Where this spec and part A §3-§5 differ, this spec wins.

All hosts, keys and user names are placeholders.

## 1. Problem

The v0.2 UI opens on a lazygit-style panel layout. Plans are a flat list of keys in a left column that is 20 to 40 columns wide, so the first screen shows names only: to see which plans are failing, the user must select each plan in turn. There is no view of every plan with its state side by side.

This spec adds a k9s-style home screen: one full-width table of every plan in the configured projects, with the last build's state, number, age and trigger, sortable and filterable, plus a small `:` command bar. `enter` on a plan opens today's panel layout for that plan. The panels, the build detail, the watch, the logs and the run form are unchanged.

## 2. Screens and navigation

```
bam ─► Home (full-width plans table)
         │ enter on a plan
         ▼
       Panels (v0.2 layout; that plan selected, focus Builds)
         │ esc with focus on Plans ─► Home
         │ l, or enter on a job ─► Log screen ─ esc ─► Panels
```

- `bam` and `bam ui` open on Home. The entry matrix of part A §2 is unchanged.
- `enter` on a Home row selects that plan in the Plans panel, loads its builds exactly as `enter` on the Plans panel does, switches to the panel layout and focuses Builds.
- `1`, `2`, `3` on Home do what `enter` does, then focus that panel instead of Builds.
- `:plans` from the panel layout returns to Home.

### 2.1 `esc`

`back()` resolves in this order (part A §4.1, with steps 4 and 5 changed):

1. an overlay or the `:` prompt is open → close it
2. the log screen is open → return to the panels
3. focus is Builds, Presets or Main → move focus to its parent panel
4. focus is Plans → return to Home
5. on Home with a filter set → clear the filter
6. otherwise → nothing; `q` quits

## 3. The Home table

```
 bam · work · 9.6.4 · jdoe · project all · 14 plans · sort key↑
 PROJECT  KEY          NAME             STATE      #     AGE   BY
▸OPS      OPS-NIGHTLY  Nightly          ● running   91   now   sched
 PROJ     PROJ-BUILD   Build and test   ✗ failed   482   12m   jdoe
 PROJ     PROJ-PROV    Provision lab    ✓ success    8   3h    sched

 enter builds  / filter  s sort  : command  R run  o open  ? help  q quit
```

### 3.1 Rows

- One row per plan in the **configured projects** of the connected server: `config.ProjectKeys(server)` (the repository entry, then the project file, then the server's machine entry). When no project is configured, every project on the server is listed and the header says `project all (none configured)`.
- This also changes the Plans panel, which today lists every project on the server: both screens share one load (section 4) and so show the same plans.
- A configured project that is not on the server is skipped, and the status bar says `project OPS is configured but not on work`, as `bam project list` warns.
- `P` and `:project` narrow the rows to one project, as `P` narrows the Plans panel today.
- The UI opens already narrowed when `bam --project KEY`, `bam ui --project KEY` or `default_project` names a project (MVP spec §3.5); `--project all` opens on every project. A filter naming a project the server does not have widens to every project and the status bar says `project OPS not found on work`, whether it came from the flag, `default_project` or `:project`.
- Plans with no build show `–` in STATE, `#`, AGE and BY.

### 3.2 Columns

| Column | Content |
| --- | --- |
| PROJECT | project key |
| KEY | plan key |
| NAME | plan name; takes the width left over, truncated with `…` |
| STATE | glyph and state word from `view/style`, the one definition of state colours and glyphs |
| # | last build number, right-aligned |
| AGE | time since the last build finished (`now`, `12m`, `3h`, `2d`), from the UI's clock |
| BY | the trigger, shortened from the build's reason: the user name for a manual run, `sched` for a schedule, `commit` for a change detection, `dep` for a dependency, else the first word |

Below 100 columns BY is dropped; below 80, PROJECT is dropped too. The header line and the key line always show.

### 3.3 Filter

`/` opens the filter input, as on the panels. It matches case-insensitively against key, name, project and state word, so `/fail` keeps failed plans. The header shows the active filter. `esc` in the input cancels the edit; `esc` on Home with a filter set clears it (section 2.1).

### 3.4 Sort

- Default: project, then plan key, ascending. The default is stable, so rows do not move on refresh.
- `s` cycles the sort column: key, name, state, age, then key again. Moving to a column sorts it in its natural direction: key and name ascending; state with failed first, then running, queued, cancelled, not built, success; age with the newest first.
- `:sort <column>` sets a column; a leading `-` reverses it (`:sort -age` is oldest first).
- Ties break on plan key, so the order is always total.
- The header shows the column and `↑` or `↓`. The sort lasts for the session and is not saved.

Shift-letter sort keys, as k9s uses, would collide with the existing keymap (`N`, `S`, `P`, `R`, `C` are taken), which is why sort uses `s` and `:sort`.

### 3.5 Keys on Home

| Key | Action |
| --- | --- |
| `j k ↑ ↓ g G` | move |
| `enter` | open the panel layout for the row's plan |
| `1 2 3` | open the panel layout with that panel focused |
| `/` | filter |
| `s` | next sort column |
| `:` | command bar |
| `R` | run form for the row's plan (part B, unchanged) |
| `o` `y` | open or copy the plan's Bamboo URL |
| `r` | refresh now |
| `S` `P` | switch server, filter by project, as today |
| `e` | expand the current error |
| `?` | help |
| `q` `ctrl-c` | quit |

`keys.go` stays the only source of the help overlay's key table. The overlay gains a HOME section and a COMMANDS section (section 5).

### 3.6 Presets table

`:presets` shows the presets of the connected server as a full-width table on Home instead of the plans: `TARGET PLAN BRANCH STATE # AGE`, where the state columns come from the row of the preset's plan (its master plan, not its branch) in the plans load, and show `–` when that plan is not in the configured projects. `enter` opens the panel layout on the preset's plan, as `enter` on the Presets panel does. `R` opens the run form for the preset. `:plans` returns to the plans table. Filter and sort apply the same way; its sort columns are target, plan, state and age.

## 4. Loading and refresh

### 4.1 One load

Home and the Plans panel share one plans load (`plansGen`), extended so a failed project does not fail the others:

- One `ListPlans` per configured project. A project that fails keeps its rows from the previous load, if any, and its error goes to the status bar. The projects that loaded update.
- `ListPlans` already fills each plan's last build with `ListBuilds(limit 1)`, eight requests at a time. That cost stays: one request per plan per refresh. The header's plan count makes it visible.
- Drilling into a plan does not reload plans.

### 4.2 Auto-refresh

- Every 30 seconds, while Home is the visible screen and no overlay is open, the plans reload.
- The refresh stops after 10 minutes with no key pressed and resumes on the next key. Part A's rule "a parked UI makes no requests" therefore still holds once the user walks away.
- The tick is a `tea.Tick` carrying a generation number (`homeTickGen`). Leaving Home, switching server or project, or a manual `r` bumps it, so an old tick cannot start a second refresh loop.
- A refresh already in flight is not started again; the tick waits for the next interval.

### 4.3 While and after refreshing

- The old rows stay on screen during a refresh; the header shows `refreshing…`.
- When the rows arrive, filter and sort are reapplied and the cursor stays on the same plan key. If that plan is gone, the cursor stays on the same row index, clamped.
- On a failed refresh the rows stay, the error's `What` goes to the status bar (`e` for detail), and the header shows `stale 3m`, the age of the last successful load.
- Responses from an older generation are dropped by the existing `currentStream` check.

### 4.4 Running marker

The last-build query lists finished builds only, so a running build of an arbitrary plan does not show. Two cases are shown from the UI's own state:

- The build the UI is watching (part A §5: at most one watch) shows its live state on its plan's row: `● running`, `◌ queued`.
- A build triggered from the UI with `R` shows `◌ queued` on its plan's row until the watch that follows it takes over.

On `EventDone` the row takes the finished state, number and age from the event without waiting for the next refresh. Other plans' running builds appear only once they finish. Listing them needs `includeAllStates` on the last-build query, a follow-up (section 9).

## 5. The `:` command bar

`:` opens a one-line prompt at the bottom of Home or the panel layout. It does not open while a text input has focus: the filter, the run form, or log search.

| Command | Action |
| --- | --- |
| `:plans` | Home, plans table |
| `:presets` | Home, presets table |
| `:project KEY`, `:project all` | filter by project, as `P` |
| `:server ALIAS` | switch server, as `S` |
| `:sort COLUMN`, `:sort -COLUMN` | sort Home (section 3.4) |
| `:q`, `:quit` | quit |

- `tab` completes the command name, then its argument: project keys from the configured projects, server aliases from `Deps.Servers`, sort columns of the current table.
- Up to five candidates show on the status line, after the prompt, as the user types.
- A unique prefix is accepted (`:pro OPS`). An ambiguous or unknown command, or a bad argument, closes the prompt and puts `unknown command "x"; commands: plans presets project server sort quit` (or the argument's error) in the status bar. Nothing else changes.
- `enter` runs the command; `esc` cancels.
- No history and no aliases.
- One command table in `command.go` feeds the prompt, the completion and the help overlay's COMMANDS section.

## 6. Architecture

Layering is unchanged: all new code is in `internal/view/tui`, which imports `app`, `provider`, `errs` and `view/style` as today.

| File | Change |
| --- | --- |
| `internal/app/service.go` | `func (s *Service) ProjectKeys() []string`, returning `s.Cfg.ProjectKeys(s.Server)`, so the UI does not reach into `config` |
| `internal/view/tui/model.go` | `screenHome` becomes the start screen; `back()` gains steps 4 and 5; `Update` hands Home keys, the prompt and ticks to the new files with one `case` each |
| `internal/view/tui/msgs.go` | `loadPlansCmd` loads `svc.ProjectKeys()` (or every project when empty) and returns per-project results and errors |
| `internal/view/tui/home.go` (new) | Home and presets tables: columns and width fitting, `homeSort{col, desc}`, filter matching, drill into the panels |
| `internal/view/tui/command.go` (new) | command table, prefix matching, completion, prompt input |
| `internal/view/tui/refresh.go` (new) | auto-refresh tick and generation, idle cut-off, merge that keeps the cursor on a key, stale age, running marker |
| `internal/view/tui/keys.go` | `s` and `:`; help sections HOME and COMMANDS |
| `internal/view/tui/list.go` | `listState` gains an optional ordering function, so sorting reuses the filtered, windowed list |

`model.go` is already the largest file in the package. New behaviour goes in the new files; `model.go` only routes to them.

## 7. Testing

The existing patterns hold: model tests drive `Update` with a fake `Deps`, `fake.Provider` and an instant clock; no terminal, no network, no sleeps. Golden views live in `internal/view/tui/testdata` and are regenerated only after an intended renderer change.

- **`home_test.go`:**
  - golden views at 120x30, 90x30 and 80x24 (column dropping)
  - `/` matching on key, name, project and state
  - every sort column in both directions, and ties broken by key
  - `enter` lands on the panels with the plan selected and its builds loading
  - `esc` with focus on Plans returns Home; `esc` on Home clears the filter
  - the presets table and its `enter`
- **`command_test.go`:**
  - every command's action
  - a unique prefix is accepted; an ambiguous or unknown one is a status error with no state change
  - completion candidates for command names and each argument kind
  - `:` does nothing while a text input has focus
- **`refresh_test.go`:**
  - a tick on Home starts a load; a tick on another screen, with an overlay open, or from an old generation does nothing
  - the idle cut-off and the resume on the next key
  - the cursor stays on the same plan key after a refresh that reorders rows
  - a failed project keeps its old rows while the others update; a failed refresh shows `stale`
  - watch events set and clear the running marker; `EventDone` updates the row
- **`msgs_test.go`:** `loadPlansCmd` uses the configured projects, falls back to every project, and skips an unknown configured project with a warning.
- **Existing tests** that assume the UI starts on the panels get a first step that drills in; their assertions do not change.
- **Before finishing:** `go test -race ./...`, `make lint`, `make docs`.

## 9. Out of scope

- Running and queued builds of plans the UI is not watching (`includeAllStates` on the last-build query; needs the capability probe and recorded fixtures first).
- A table at every level (builds, stages, jobs), and `:builds`, `:logs`, `:run` commands.
- Command history and aliases.
- Saving the sort or the last screen between sessions.
- Changes to the build detail, the watch, logs, the run form or cancel.

## 10. Acceptance

- `bam` opens on a full-width table of every plan in the configured projects, with state, number, age and trigger of each plan's last build.
- `/fail` keeps the failed plans; `s` and `:sort -age` reorder the table; the cursor stays on its plan across a refresh.
- `enter` opens the v0.2 panels for that plan; `esc` from the Plans panel returns to the table.
- The table refreshes every 30 seconds while visible, stops after 10 idle minutes, and a failing project does not blank the others.
- `:project OPS`, `:server work`, `:presets`, `:plans` and `:q` work, with `tab` completion.
- The build the UI watches shows as running on its row and turns to its final state when it ends.

# Bam v0.3 - Build duration estimate and progress bar

**Status:** Implemented | **Date:** 2026-09-20
**Product requirements:** [`docs/prd.md`](../../prd.md) §7 "Then (v0.3)"
**Builds on:** [`2026-09-12-bam-cli-mvp-design.md`](2026-09-12-bam-cli-mvp-design.md), [`2026-09-18-bam-v0.2-tui-navigate-design.md`](2026-09-18-bam-v0.2-tui-navigate-design.md), [`2026-09-18-bam-v0.2-tui-actions-design.md`](2026-09-18-bam-v0.2-tui-actions-design.md)

This spec covers the build duration estimator alone. The other v0.3 items (`run --edit`, `run --revision`, `run --verbose`, `bam target sync`) are separate work with their own designs. All hosts, keys and user names are placeholders.

## 1. Summary

A watched build currently shows how long it has been running. It does not show how long it is likely to take. This adds the missing half: a progress bar, a percentage and a remaining time, on the live watch block, in the terminal UI's build detail, on `bam build show`, in `bam build list`, and in the JSON and NDJSON documents.

The estimate comes from Bamboo, not from bam. Bamboo already computes `averageBuildDuration` per plan and reports a running build's progress against it. Bam reads that number and renders it. Bam computes no statistic of its own, keeps no history sample, and caches no estimate.

Where the server cannot answer, bam shows what it shows today. A missing estimate is never an error, never a warning, and never a placeholder that shifts the layout.

## 2. Data source

`GET /rest/api/latest/result/status/{buildKey}` on a running build:

```json
{
  "currentStage": "Deploy",
  "finished": false,
  "progress": {
    "isValid": true,
    "averageBuildDuration": 180000,
    "buildTime": 99000,
    "percentageCompleted": 0.55,
    "prettyTimeRemaining": "1 minute remaining"
  }
}
```

Bam reads `currentStage`, `progress.isValid`, `progress.averageBuildDuration`, `progress.buildTime` and `progress.percentageCompleted`. It ignores `prettyTimeRemaining` and every other pretty-printed field: bam formats durations its own way, with `view.Duration`, so the estimate reads like every other duration in the tool.

The endpoint answers for running builds. A finished or queued build yields no estimate.

The field names above first came from Bamboo's REST documentation. A recording from the owner's personal Bamboo 12.1.8 (`testdata/recorded/status_running.json`) confirms all five fields bam reads, with the same names and types. The real payload also carries `expand`, `key`, a `stages` summary, and more pretty-printed fields such as `startedTime` and `prettyAverageBuildDuration`; bam reads none of them. The hand-written fixture encodes the shape above, and `TestRecordedStatusDecode` decodes the recording through the same client. If a later recording disagrees, the DTO and the mapping change; nothing above the `bamboo` package changes.

### Rejected alternative

Computing the estimate locally from `ListBuilds` history (a median of the last N successful builds of the same branch) was considered and rejected for v0.3. It doubles the code under test, needs a sample cache with its own staleness rules, and produces a second number that can disagree with the one Bamboo shows in its own web UI. If a target server turns out to lack the status endpoint, the local estimator becomes a real proposal again, with its own spec. A server without the status endpoint now gets a local estimate: see [`2026-10-07-bam-local-estimate-design.md`](2026-10-07-bam-local-estimate-design.md).

## 3. `provider`: one type, one method

```go
// Progress is how far a running build has got, as the server reports it.
// The zero value means "no estimate", which is not an error.
type Progress struct {
	Valid     bool          // the server had a usable estimate
	Average   time.Duration // averageBuildDuration for this plan
	Elapsed   time.Duration // build time so far, as the server counts it
	Remaining time.Duration // Average - Elapsed, floored at zero
	Percent   float64       // 0..1, clamped; 1 once Elapsed >= Average
	Stage     string        // currentStage, may be empty
}
```

```go
// BuildProgress reports how far a running build has got. A queued or finished
// build yields a zero Progress and a nil error. A server without the endpoint
// yields an error wrapping errs.ErrUnsupported.
BuildProgress(ctx context.Context, buildKey string) (Progress, error)
```

`Build` is untouched. No existing JSON document, golden file or fixture changes shape because of this method.

`provider/fake` gains `Progressions map[string][]provider.Progress`, walked per build key exactly as `Sequences` is walked, repeating the last entry, plus `ProgressErr` for the unsupported and transport cases.

## 4. `provider/bamboo`: capability-gated read

`Capabilities` gains one field, `Progress string` (`yes` | `no` | empty for "not yet known"), cached per origin in `$XDG_CACHE_HOME/bam/capabilities.json` with the existing seven-day and version-change staleness rules.

`BuildProgress` follows the shape `failedTests` already uses:

1. `c.fresh(ctx)`; when `caps.Progress == "no"`, return `errs.ErrUnsupported` without a request.
2. `GET /rest/api/latest/result/status/{key}`.
3. `isUnsupportedStatus(err)` (400, 404, 405, 501) → `learn(Progress = "no")`, return `errs.ErrUnsupported`.
4. Any other transport error → return it unchanged, learn nothing. A timeout does not mean the feature is missing.
5. Success → `learn(Progress = "yes")` when not already known, map the DTO.

Mapping rules:

- `finished == true`, or `progress` absent, or `isValid == false` → `Progress{}`, nil error.
- `Average = averageBuildDuration ms`, `Elapsed = buildTime ms`.
- `Remaining = max(0, Average - Elapsed)`.
- `Percent = clamp(percentageCompleted, 0, 1)`; when `percentageCompleted` is absent and `Average > 0`, `Percent = clamp(Elapsed / Average, 0, 1)`.
- `Valid = Average > 0`.

`doctor` gains a "duration estimate" row: `yes` → "read from PROJ-PLAN-44"; `no` → unsupported, "watch shows elapsed time only"; unknown → skipped, "learned the first time a running build is watched".

## 5. `app`: progress on every poll

`Event` gains one field, `Progress provider.Progress`. Progress rides the events that already exist, so every renderer and the terminal UI see it without a new channel or a new message.

A poll that changes no state still brings a fresh estimate, and riding only on changes would freeze the bar while a job runs steadily. So `Watch` sends one more type, `EventProgress`, when a poll produces no other event and its valid estimate differs from the one the last event carried. It does not count as a change: the poll backoff keeps growing. `Live` and the terminal UI redraw from it like any other event. `Lines` and `NDJSON` skip it, so pipe output and the NDJSON types of the v0.1 spec §7 stay as they are.

In `Watch`, after `s.Build` succeeds and before `diff`:

```go
pr, err := s.P.BuildProgress(ctx, key)
if err != nil {
	pr = provider.Progress{}
	if errors.Is(err, errs.ErrUnsupported) {
		noProgress = true // loop-local; skip the call for the rest of this watch
	}
}
```

Rules:

- A progress error never produces an `EventError` and never ends a watch. The build's state is the thing being watched; the estimate is decoration.
- The first `errs.ErrUnsupported` sets a loop-local flag, so one watch makes at most one failed call. The capability cache makes that decision stick across processes.
- `EventDone` carries the zero `Progress`: a finished build has a duration, not an estimate.

One-shot callers use:

```go
// Progress returns how far a running build has got. An unsupported server or a
// build that is not running yields a zero Progress and a nil error.
func (s *Service) Progress(ctx context.Context, key string) (provider.Progress, error)
```

It swallows `errs.ErrUnsupported` into a zero `Progress` and returns real transport errors, which every caller in this spec then ignores. `app` still prints nothing, reads no stdin and imports no cobra; `TestAppStaysUIReady` and `imports_test.go` are unchanged.

## 6. `view`: the bar

New file `internal/view/progress.go`:

```go
// Bar renders a progress bar, a percentage and a remaining time. It returns
// "" when there is no estimate, so callers may append it unconditionally.
func Bar(o Out, p provider.Progress) string
```

- Returns `""` when `!p.Valid` or `p.Average == 0`. No placeholder, no layout shift.
- Cell count: `min(24, max(10, o.Width/4))`; `o.Width == 0` means 20.
- `style.Mode` with color: `[████████░░░░░░░░]  55%  ~1m20s left`.
- `style.Mode` without color (pipe, `--no-color`): `[########--------]  55%  ~1m20s left`.
- Overrun, `Elapsed >= Average`: full bar, `100%  over by 30s`. Never a negative remaining, never a bar stuck below 100%.
- Durations are formatted by `view.Duration`, so `~1m20s left` matches the elapsed time beside it.

`Live` (the TTY watch block) keeps the last `Progress` and the wall-clock time it arrived. `Live.Tick`, driven by the existing one-second ticker in `internal/cli/runloop.go`, extrapolates between polls: `elapsed = p.Elapsed + (Now - receivedAt)`, recomputing percent and remaining locally. The bar therefore moves every second, toward a number the server refreshes on every poll. `block()` appends the bar to the header line, after the elapsed duration.

`Lines` (one timestamped line per change, for pipes and CI logs) gets no bar. There is nothing to redraw in a pipe, and its output is a contract that scripts read. It stays byte for byte as it is today.

`bam build show` gains one line, on a running build only:

```
Estimate  3m00s   [████████░░░░░░░░]  55%  ~1m20s left
```

`bam build list` gains an `ETA` column, filled only for rows in state `running`, empty for every other row and omitted entirely when no row is running. This costs one `BuildProgress` call per running row. Listings normally show zero or one running build; a plan with several running branches pays one call each, and no call is made for the rows that cannot have an estimate.

## 7. Terminal UI

- `watchEventMsg` carries `provider.Progress`; the model keeps it beside `m.detail` and clears it when the detail changes to another build.
- `detailBody`'s header line appends `view.Bar` at the panel's width.
- The command that loads a build for the detail panel also calls `Service.Progress`, so opening a running build shows a bar before the first watch poll lands.
- The UI has no ticker today, so the bar advances once per watch poll (2-10s) rather than once per second. Adding a `tea.Tick` is deliberately out of scope: it touches the update loop and every golden file for smoothness alone.

## 8. JSON contract

Additive only, per MVP spec §7. No field is renamed and none is removed.

```json
"progress": {
  "percent": 0.55,
  "average_ms": 180000,
  "elapsed_ms": 99000,
  "remaining_ms": 81000,
  "stage": "Deploy"
}
```

- `BuildDoc.Progress` is a `*ProgressDoc` with `omitempty`: the key is absent when there is no estimate, rather than present and zero.
- `bam build show --json` and `bam build list --json` carry it for running builds.
- NDJSON watch events carry the same object on `state`, `stage` and `job` lines, and never on `done` or `error`.
- `percent` is the clamped 0..1 float, not a percentage string.

## 9. Testing

- `provider/bamboo`: hand-written fixture `testdata/status_running.json`; tests for the running mapping, `finished: true` and `isValid: false` both yielding a zero `Progress` with a nil error, 404 yielding `errs.ErrUnsupported` and learning `Progress = "no"`, a cached `no` making no second request, and a 500 leaving the capability unknown. `TestRecordedStatus` checks the hand-written shape against `testdata/recorded/`.
- `provider/fake`: `Progressions` walks like `Sequences`.
- `app`: progress attached to every event of a poll; an unsupported provider degrading to a zero `Progress` with no `EventError` and no second call; `EventDone` carrying a zero `Progress`.
- `view`: explicit expected strings for `Bar` at several widths, with and without color, at 0%, mid-build and overrun, and `""` for an invalid estimate; a golden file for the watch block with a bar; `Lines` output unchanged.
- `view/tui`: golden files for a running build with and without an estimate.
- `cli`: harness tests for `build show` and `build list` with a running build, and JSON tests for `progress` present and absent.
- No test sleeps and none touches the network: the fake clock, `fake.Provider` and `httptest` as everywhere else.

## 10. Acceptance criteria

1. `bam watch PROJ-PLAN-44` on a running build shows a bar that advances every second and a remaining time that tracks the server's estimate.
2. The same build in `bam` (the terminal UI) shows the same bar in the detail panel.
3. `bam build show PROJ-PLAN-44` prints an `Estimate` line while the build runs and no such line once it finishes.
4. `bam build list PROJ-PLAN` shows an `ETA` for running rows only.
5. `bam watch --json` emits `progress` on running events and omits it on `done`.
6. Against a server without the status endpoint, every command above behaves exactly as it does today, `bam doctor` reports the feature as unsupported, and at most one probe request is made per origin per seven days.
7. `make test`, `go test -race ./...`, `make lint`, `make check-fixtures` and `make docs` all pass.

## 11. Out of scope

- A local history estimator, a sample cache, and per-stage estimates.
- A second-resolution ticker in the terminal UI.
- Estimates for queued builds (queue time is not build time) and for deployment projects.
- `run --edit`, `run --revision`, `run --verbose`, `bam target sync`: separate v0.3 work.

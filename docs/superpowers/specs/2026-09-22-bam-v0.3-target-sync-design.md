# bam v0.3: `bam target sync`

**Status:** Implemented | **Date:** 2026-09-22

## 1. Problem

`bam target add` and `bam init --plan` write a preset from a plan's declared variables. Plans change afterwards: a new variable appears, an old one is removed. Today the preset silently falls behind. A new variable runs with its plan value and never shows up in `target show`. A removed one stays in `defaults`, and `run` warns about it on every trigger without saying why.

`bam target sync` brings a preset back in line with its plan without touching anything a person wrote.

## 2. Command

```
bam target sync <name> [--dry-run]
bam target sync --all  [--dry-run]
```

- Exactly one of `<name>` or `--all` is required; both, or neither, is a usage error (exit 2).
- `<name>` must be a configured target; an unknown name is a usage error with `Try: bam target list`.
- `--all` syncs every merged target (`config.Targets()`), sorted by name.
- `--dry-run` computes and prints every change and writes no file.
- `--json` prints the result document of section 6.
- Shell completion for `<name>` uses the existing `completeTargets`.

Each target connects to its own server, selected exactly as `bam run <target>` selects it (`--server`, `BAM_SERVER`, ..., the target's `server` key; spec §3.5 of the MVP design). Under `--all`, targets that resolve to the same server share one connection.

## 3. What changes

Sync generates a fresh draft with the existing generator (`app.GenerateTarget`, MVP spec §3.9) from the target's `plan` and `branch`, then compares the draft with the target's merged `defaults`.

| Case | Condition | Action |
| --- | --- | --- |
| Added | the plan declares a name the target's `defaults` lacks, and lean `target add` would write it | insert `name: "value"  # comment` into `defaults`, value and comment exactly as `target add` would write them |
| Stale | the target's `defaults` has a name the plan does not declare | keep the entry; add the trailing marker `not declared on PROJ-PLAN` |
| Re-declared | an entry carries the marker and the plan declares the name again | remove the marker |
| Unchanged | the name is in both | nothing; the value is never overwritten |

Rules:

- Added follows `target add`'s lean rule (MVP spec §3.9): a name with a non-empty plan value, including a secret the plan stores, is not added, since the plan already sends it. A new name with no plan default, or an empty secret, is added. Otherwise a lean preset would get every plan default copied back on its first sync.
- Sync never changes an existing value, and never touches `plan`, `server`, `branch`, `options`, `required`, `watch` or `timeout`.
- Added values follow the generator's secret rules: a value Bamboo returns masked, or a name matching the masked-name pattern, is written as `"${NAME_IN_UPPER_SNAKE}"` with the comment `masked by Bamboo; set env var NAME_IN_UPPER_SNAKE`.
- A stale entry's existing trailing comment is kept; the marker is appended to it after `; `. A marker already present is not added twice.
- A stale name may be a Bamboo global variable the plan overrides; the plan variable endpoint does not list globals (MVP spec §2). That is why stale entries are kept, never removed.
- A target with no changes is reported `up to date` and its files are not rewritten, so their bytes and modification times stay the same.
- If the plan variable endpoint is unsupported on the server, the target fails with a Bamboo error (exit 5): `cannot read plan variables of PROJ-PLAN on this server`. Sync does not fall back to build variables as `target add` does: without the declared list it cannot tell a stale name from a current one.
- A plan that no longer exists fails the target with the provider's error (exit 5).

## 4. Which file is written

A target merges from up to three layers, lowest precedence first: the project file `targets`, the machine file `targets`, and the machine file `repos.<root>.targets`.

- **Added** names go into the layer that sets the effective `plan`, which is the last layer with a non-empty `plan`. That is the file `target add` or `init` wrote. A `defaults` mapping is created there when missing.
- **Stale markers** and **re-declared** marker removals go on every layer's own entry for that name.
- Edits go through the yaml.v3 Node API in `internal/config/edit.go`, like `WriteTarget`, so comments, key order and the file mode survive. New keys are appended at the end of `defaults`.

To address a layer, `config.ResolvedTarget` gains `Layers []TargetLayer`, lowest precedence first:

```go
type TargetLayer struct {
	Path    string   // file on disk
	KeyPath []string // mapping path to the targets map, e.g. ["targets"] or ["repos", root, "targets"]
	Target  Target   // this layer's raw entry
}
```

`DefinedIn` keeps its current values, including the ` (repos)` suffix, because `target show` and the `--json` contract use it.

## 5. Architecture

| Package | Addition |
| --- | --- |
| `config` | `TargetLayer`, `ResolvedTarget.Layers`; `TargetEdit`, `TargetChange`, `StaleMarker(plan)`; `SyncTarget(path, keyPath, name, TargetEdit, write bool) (TargetChange, error)` |
| `app` | `SyncPlan`, `SyncEdit`, `(*Service).PlanSync(ctx, config.ResolvedTarget) (SyncPlan, error)`, `DisplayDraftValue`; the generator gains an internal variant that reports whether the names came from the declared list |
| `view` | `SyncResult`, `Sync(o, results, dryRun)` text renderer, `SyncDoc` / `SyncJSON` |
| `cli` | `newTargetSyncCmd` under `target`; applies each `SyncEdit` through `config.SyncTarget`, with `write` false under `--dry-run` |

`app` computes and never writes files; `cli` applies. This keeps `app` UI-ready (`TestAppStaysUIReady`) and lets the terminal UI reuse `PlanSync` later.

```go
type SyncPlan struct {
	Name  string
	Plan  string
	File  string            // file that receives Added
	Added []config.DraftVar // declared on the plan, missing from defaults; in plan order
	Stale []string          // in defaults, no longer declared on the plan; sorted, never nil
	Edits []SyncEdit        // one per layer with something to do, lowest precedence first
}

type SyncEdit struct {
	Path    string
	KeyPath []string
	Edit    config.TargetEdit // Add (plan layer only), Mark (stale names in this layer), Unmark (declared names in this layer), Plan
}
```

`app` does not read YAML comments, so it cannot know which entries already carry a marker. `SyncTarget` is therefore idempotent: marking a marked name, unmarking an unmarked one, or adding an existing name is a no-op, and the returned `TargetChange` lists only real edits. A target is `up to date` when every edit's change is empty. With `write` false the change is computed and nothing is written.

## 6. Output

Text, one block per target:

```
provision-lab  PROJ-PROV  .bam.yaml
  +  region       ""              no plan default
  +  api_token    "${API_TOKEN}"  masked by Bamboo; set env var API_TOKEN
  !  old_flag                     not declared on PROJ-PROV (kept)
  ~  zone                         declared again on PROJ-PROV (marker removed)
build  PROJ-BUILD  .bam.yaml  up to date
```

- Stale names are listed on every run while they stay undeclared, including on an `up to date` target; `~` lines appear only on the run that removes a marker.
- The file is shown relative to the repository root when inside it, else as an absolute path.
- A failed target prints `name  PLAN  error: <what>` and sync moves on to the next.
- With `--dry-run` the header of a target with changes is prefixed `would sync:` and a final line reads `dry run: no files written`.
- After any write, stderr prints `review before commit: values copied from Bamboo`.
- Values of names matching the masked-name pattern print as `********`; `${ENV}` references print as written, as in `target show`.

`--json` prints an array, one object per target:

```json
[
  {
    "name": "provision-lab",
    "plan_key": "PROJ-PROV",
    "file": "/home/jdoe/src/repo/.bam.yaml",
    "status": "synced",
    "added": [{"name": "region", "value": "", "comment": "no plan default"}],
    "stale": ["old_flag"],
    "redeclared": [],
    "error": ""
  }
]
```

- `status` is `synced`, `up_to_date`, `would_sync` (with `--dry-run`), or `error`.
- `added`, `stale` and `redeclared` are always arrays, never null. `error` is empty unless `status` is `error`.
- Field names follow the existing `--json` contract style (`plan_key`, `defined_in`) and, like every `--json` field, are only ever added to, never renamed or removed.

## 7. Exit codes

- One target: its error's code (MVP spec §8), or 0.
- `--all`: every target is attempted. The exit code is the highest per-target code; errors are printed inline (text) or in `error` (JSON), not again at the end.

## 8. Testing

- `config`: `Targets()` fills `Layers` for all three layers; `SyncTarget` golden tests on a hand-commented file: added keys appended with comments, marker appended to an existing comment, marker removed leaving the original comment, `defaults` created when missing, file mode kept, no write for an empty change set.
- `app` over `fake.Provider`: added (plain, no plan default, masked), stale, re-declared, unchanged, unsupported plan variables (exit 5, no fallback), added names targeting the last layer with `plan`, stale marks on every layer defining the name.
- `cli` harness: `target sync provision-lab` writes and a second run reports `up to date` with identical bytes; `--dry-run` writes nothing; `--all` continues past a failing target and exits with its code; `--json` shape; name and `--all` together, or neither, exit 2; unknown target exits 2.
- `make docs` regenerates `docs/cli/bam_target_sync.md` and `bam_target.md`.

## 9. Acceptance

1. After adding a variable to a plan on the personal Bamboo, `bam target sync <name>` adds it to the preset with a `# no plan default` comment when it has no default (a variable with a default is left to the plan) and leaves every other line of the file as it was.
2. After removing a plan variable, sync keeps the entry and marks it `not declared on PROJ-PLAN`; re-adding the variable and syncing again removes the marker.
3. A second sync with no plan change reports `up to date` and does not modify the file.
4. `bam target sync --all --dry-run --json` lists every target's changes and writes nothing.
5. `make test`, `go test -race ./...`, `make lint`, `make check-fixtures` and `make docs` pass.

## 10. Out of scope

- Removing stale entries (a `--prune` flag). Revisit if stale markers pile up in practice.
- Updating `options` or `required` from the plan.
- Rewriting values whose plan default changed.
- A sync action in the terminal UI.

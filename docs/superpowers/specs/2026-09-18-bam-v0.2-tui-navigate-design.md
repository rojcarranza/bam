# Bam v0.2 - Terminal UI, part A: navigate and watch

**Status:** Implemented | **Date:** 2026-09-18
**Product requirements:** [`docs/prd.md`](../../prd.md) §7 "Next (v0.2): terminal UI"
**Builds on:** [`2026-09-12-bam-cli-mvp-design.md`](2026-09-12-bam-cli-mvp-design.md), especially §8.5

This spec is the input to the v0.2 part A implementation plan. All hosts, keys and user names are placeholders.

## 1. Summary

Running `bam` alone on a terminal opens a lazygit-style terminal UI over the same `app` use cases the commands call. It adds no behaviour the commands lack.

v0.2 is delivered in two specs. **Part A, this one, is read-only:** browse plans, builds, stages and jobs, watch a build live, read logs, switch server, project and branch, and reach Bamboo by browser or clipboard. No key in part A triggers, cancels or edits anything.

**Part B, a later spec,** adds the mutating actions: run a preset or a plan, the variable form prefilled from the preset or a previous build, and cancel.

Splitting this way lets part A ship on its own, proves the framework and the panel shell against a real Bamboo, and means a mis-keystroke in an early build cannot start a build.

## 2. Entry points

| Invocation | Behaviour |
| --- | --- |
| `bam` on a terminal | opens the UI |
| `bam` on a pipe, or with `TERM=dumb`, or stdin not a terminal | prints help, exactly as v0.1 minus the "interactive mode arrives in v0.2" line |
| `bam --no-tui` | prints help; never opens the UI |
| `BAM_NO_TUI=1 bam` | prints help; never opens the UI |
| `bam ui` | opens the UI; fails with a config-kind error when there is no terminal |
| `bam <command>` | unchanged |

"On a terminal" means stdout and stdin are both TTYs and `TERM` is neither empty nor `dumb`. `cli.Env` already carries `StdoutTTY` and `StdinTTY`; `TERM` is read through the injected `Getenv`, so the gate needs no new `Env` field for detection.

`Env` does gain one field, `RunTUI func(context.Context, tui.Deps) error`, defaulting to `tui.Run`. That is the seam the in-process CLI harness replaces: the entry matrix is tested by asserting which path ran and with which `Deps`, without ever starting a `tea.Program`.

`--no-tui` is a persistent flag so it can sit in an alias. `BAM_NO_TUI` is read through the injected `Getenv`.

## 3. Layout

> Superseded in part by [the v0.3 home table design](2026-09-23-bam-v0.3-tui-home-design.md): bam now opens on a plans table, and esc from Plans returns to it.

At 80x24, the smallest supported size:

```
┌─1 Plans ───────────┐┌─ PROJ-BUILD-44 ──────────────────────────┐
│▸ PROJ-BUILD        ││ ✗ failed   #44   branch main   3m12s     │
│  PROJ-DEPLOY       ││ jdoe · manual · a1b2c3d                  │
│  OPS-NIGHTLY       ││                                          │
└────────────────────┘│ ✓ Build       42s                        │
┌─2 Builds ──────────┐│   ✓ Compile        28s                   │
│▸ ✗ #44  3m ago     ││   ✓ Unit tests     14s                   │
│  ✓ #43  1h ago     ││ ✗ Test        2m30s                      │
│  ✓ #42  3h ago     ││   ✗ Integration    2m30s                 │
└────────────────────┘│ – Deploy                                 │
┌─3 Presets ─────────┐│                                          │
│  provision-lab     ││ 3 failed tests                           │
│  smoke             ││                                          │
└────────────────────┘└──────────────────────────────────────────┘
 lab · 9.6.4 · jdoe          ?help  tab focus  l logs  o open  q quit
```

- **Left column**, fixed at three panels, numbered so `1`, `2`, `3` focus them directly: Plans, Builds, Presets. The left column is 25% of the width, minimum 20 columns, maximum 40.
- **Main panel** renders what the focused left panel points at: plan detail for Plans, build detail with the stage and job tree for Builds.
- **Status bar**, one line: the current server alias, its Bamboo version and the current user on the left; context keys on the right. Errors replace the left half until dismissed.

Panels are unnumbered for projects and servers. The Plans panel is one flat list of `PROJECT-PLAN` keys across every project of the current server, filtered with `/`. Server and project are chosen in overlays. That keeps every row of a 24-row terminal for content and scales past a hundred plans, which a stacked projects panel does not.

### 3.1 Log screen

> Follow and search are superseded by [the live stage logs design](2026-10-10-bam-tui-live-stage-logs-design.md): `l` on a stage or a running build streams the stage, multi-job screens prefix each line with its job, and search highlights and counts matches as lines arrive.

`l` hides the left column and gives the log viewport the whole width:

```
PROJ-BUILD-INT-44 · logs · failed                            1842/1842
12:04:31  [INFO] Running integration suite
12:06:58  [ERROR] ConnectionRefused: bamboo.lab.example:5432
12:06:58  [ERROR] 3 tests failed
12:07:01  Finished with exit code 1

esc back  / search  G end  f follow  n next failure  o open
```

The header names the job result key, the source (`failed` or `all`) and the position in the log. `esc` restores the columns.

The log screen is the one screen with no border: the whole point of taking the terminal is room for lines, and a box costs two columns of width and two rows of height for decoration. The header and the key line are the frame.

### 3.2 Overlays

Centred, bordered, at most 60 columns wide: server picker, project filter, branch picker, help, error detail. One overlay at a time. `esc` closes it.

## 4. Keymap

> Superseded in part by [the v0.3 home table design](2026-09-23-bam-v0.3-tui-home-design.md): bam now opens on a plans table, and esc from Plans returns to it.

`keys.go` holds one `key.Binding` set and it is the only source of the help overlay's table.

```
MOVE      j k ↑ ↓         up / down in the focused panel
          g G             first / last row
          tab shift-tab   next / previous panel
          1 2 3           focus Plans / Builds / Presets
          enter           drill in
          esc             back out one level, close an overlay

VIEW      l               logs for the selection (failed jobs by default)
          a               all logs, not only failed
          f               follow (log screen)
          /               filter the focused list, or search the log
          n N             next / previous match, or next failure in a log
          r               refresh the focused panel
          e               expand the current error

GO        o               open the selection's Bamboo URL in the browser
          y               copy the selection's Bamboo URL
          S               switch server
          P               filter by project
          b               switch plan branch

META      ?               help overlay
          q  ctrl-c       quit
```

`h` and `l` are not movement keys: the left column is vertical only, so `l` is free for logs. No key in part A mutates anything on the server.

### 4.1 Drill-down

| Focus | `enter` |
| --- | --- |
| Plans | load that plan's builds; focus Builds |
| Builds | render build detail; focus Main; start the watch |
| Main, on a stage | expand or collapse its jobs |
| Main, on a job | open the log screen for that job |
| Presets | select the preset's plan in Plans and load its builds |

`esc` resolves in one fixed order, implemented as `(m Model) back() Model` and tested directly:

1. an overlay is open → close it
2. the log screen is open → return to the columns
3. focus is not on Plans → move focus back one panel
4. otherwise → quit

## 5. Freshness

- Selecting a build starts `app.Watch` on it and cancels the previous watch. **At most one watch runs.** `Model` holds the `context.CancelFunc`.
- Build detail and the stage and job tree update from `app.Event` values. No second polling path exists; the adaptive 2-10s backoff in `app.Watch` is what the UI uses.
- `EventDone` cancels the watch and re-fetches the Builds list, so the finished row updates.
- `EventError` sets the status bar and stops the watch. It never tears the UI down. `r` retries.
- Plans and Presets load once per server and refresh on `r`, on a server switch or on a project filter change.
- A parked UI whose build has finished makes no requests.
- Leaving the UI cancels the watch. **Cancelling a watch never stops the build**, in the UI exactly as on the command line.

## 6. Errors

The UI does not exit on a use-case error. The `*errs.Error`'s `What` goes to the status bar in red; `e` opens the error overlay with `Why` and `Try`. An auth-kind error additionally names `bam login` in the overlay, because the UI cannot exit 4.

Exit codes: a clean quit from `bam` or `bam ui` exits 0. A failure to *start* — no terminal for `bam ui`, no server configured, the first connect failed — returns the `*errs.Error` to `cli` and maps through the existing `exitCode` unchanged.

The first connect therefore happens in `tui.Run`, **before** the bubbletea program starts: a start-up failure is an exit code, so it cannot be a message inside a UI that is already running. `Model.Init` skips connecting when that handshake already succeeded.

## 7. Secrets

The Presets panel shows a preset's name, plan and branch, and only the presets that belong to the connected server. A preset may name a server of its own, and the panel loads every configuration layer: acting on one bound to another alias would resolve its plan against a Bamboo the UI is not connected to. Switching server with `S` reloads the panel. Part A renders no variable value anywhere. Part B's variable form applies the existing rule: names matching `password|secret|passphrase|sshkey`, values Bamboo returns as `********`, and `${ENV}`-resolved values all render as `********`.

## 8. Clipboard

`y` writes the selection's Bamboo URL as an OSC 52 escape sequence. No dependency, and it reaches the system clipboard through ssh and tmux, where a local clipboard binary cannot. Not every terminal honours OSC 52, so the status bar reports "copied to clipboard (osc 52)" and the help overlay names `o` as the fallback.

## 9. Architecture

### 9.1 Packages

```
internal/view/tui/
  tui.go      Run(ctx, Deps) error — builds and runs the tea.Program
  model.go    root Model; Init, Update, View; focus and screen state
  panels.go   Plans, Builds and Presets list panels
  detail.go   build detail, stage and job tree
  logs.go     log screen: viewport, search, follow
  modal.go    server, project and branch pickers; help; error detail
  keys.go     the key.Binding set and the help table
  theme.go    lipgloss styles; the style.State to lipgloss colour adapter
  msgs.go     tea.Msg types and the tea.Cmds that wrap app calls
  osc52.go    clipboard write
internal/cli/
  ui.go       the `bam ui` command, the bare-bam gate, the Deps wiring
```

### 9.2 Dependency rule

The v0.1 table gains one row:

| Package | May import |
| --- | --- |
| `view/tui` | `provider`, `app`, `view`, `view/style`, `errs` |

`view/tui` never imports `cobra`, `config` or `provider/bamboo`. `TestTUIDependencyRule` enforces it, mirroring `TestAppStaysUIReady`. `cli` remains the only package that calls `bamboo.New`.

### 9.3 Injection

`view/tui` builds no providers and reads no configuration file. `cli` passes everything in:

```go
// Server is one entry of the server registry, as the UI needs it.
type Server struct {
    Alias string
    URL   string
}

// Deps is everything the UI needs. Every field is injectable, so the
// model tests need no network, no keychain and no terminal.
type Deps struct {
    Servers   []Server
    Initial   string                                           // alias to open with
    Connect   func(ctx context.Context, alias string) (*app.Service, error)
    Targets   func() ([]app.TargetInfo, error)                 // the Presets panel
    Open      func(url string) error                           // pkg/browser, injected
    Clipboard io.Writer                                        // where OSC 52 is written
    Output    io.Writer                                        // the tea.Program's output; nil means os.Stdout
}
```

`Targets` exists because `app.DescribeTargets` takes a `*config.Config`, and `view/tui` does not import `config`. `cli` closes over its own configuration and passes the result.

Plain listings go through the connected `*app.Service`'s `P` field, which is a `provider.Provider` — `ListProjects`, `ListPlans`, `ListBranches`, `ListBuilds`, `GetPlan`, `URL`. That is what the v0.1 commands already do in `internal/cli/browse.go`, so part A adds no new `app` method for reading.

`Connect` is `runtime.connectServer` behind a func value, which is what spec §8.5 means by "`cli` builds dependencies in one function that the UI entry point reuses".

### 9.4 One definition of state colour

`view/style` keeps owning colour and glyphs. `theme.go` holds the only adapter, `stateStyle(provider.State) lipgloss.Style`, built from the same ANSI code `style` uses. Glyphs come from `style.Glyph`. `style.Paint` is not called inside panels: lipgloss cannot measure or truncate text that already carries ANSI.

Scalar formatters are reused as they are: `view.Duration`, `view.Ago`. The v0.1 table and detail renderers are **not** reused — they write ANSI to an `io.Writer` sized for a pipe and are pinned by golden files, so sharing them would break CLI goldens on every panel change.

### 9.5 Messages

```
plansLoadedMsg   buildsLoadedMsg   presetsLoadedMsg   branchesLoadedMsg
buildMsg         watchEventMsg{app.Event}   logChunkMsg   connectedMsg
copiedMsg        errMsg{err error, where string}
```

Every `app` call is a `tea.Cmd`. Watching uses the standard bubbletea channel pattern: one command reads a single `app.Event` and returns `watchEventMsg`; handling that message re-issues the command. The channel is never ranged over inside `Update`.

**Every asynchronous message carries the generation of the request that produced it**, and the model drops any message from an older generation. There is one counter per stream — plans, builds, logs, watch, follow — bumped whenever a request is issued or a stream abandoned. Without this, a slow response for the server, project, branch, build or job the user has just left lands on the one they are looking at now, and an abandoned watch's `watchClosedMsg` cancels the watch that replaced it.

Errors are tagged the same way. A failure from a request the user has abandoned must not replace the status of the one they are waiting on, so `errMsg` carries its stream and generation too.

Every watch, follow and load hangs off the UI's own context, which `Run` passes in. bubbletea can return because that context was cancelled, without any key reaching the quit path, and a poll loop must not outlive the screen that started it.

Switching plan or branch also clears the Builds panel before loading, because the rows on screen belong to what is being left and `enter` on one of them would open a build from the wrong plan. A plain refresh keeps them, so the cursor does not jump.

`logChunkMsg` has two sources. A one-shot read comes from `app.Logs`. Following comes from `app.FollowLog`, whose `emit func([]string)` callback is adapted once, in `msgs.go`, into a channel that the same one-message-at-a-time pattern drains. `FollowLog` blocks, so it runs in its own goroutine under the follow context, and `f` toggling off cancels that context.

## 10. Dependencies

Four beyond v0.1's list. The MVP spec §12 is amended in the same branch and each commit states its reason.

| Dependency | Reason |
| --- | --- |
| `github.com/charmbracelet/bubbletea` | the Elm loop; `app.Watch`'s `<-chan Event` forwards as `tea.Msg` with no translation layer |
| `github.com/charmbracelet/lipgloss` | borders, panel sizing, width-aware truncation |
| `github.com/charmbracelet/bubbles` | `viewport` for logs, `textinput` for filters, `key` and `help` for the keymap, `spinner` |
| — | no clipboard dependency of bam's own: OSC 52 is written by hand in `osc52.go` |

`bubbles/textinput` pulls `github.com/atotto/clipboard` in transitively, for its own paste support. bam never calls it: `y` writes OSC 52, for the reasons in §8. The module appears in `go.mod` as an indirect dependency only.

Pinned versions, resolved together and compile-checked against the widgets this spec names: `bubbletea v1.3.10`, `lipgloss v1.1.0`, `bubbles v0.21.1`. bubbles v1.0.0 exists but tracks bubbletea v2; part A stays on the v1 line. Moving to v2 is its own commit, after part B.

## 11. Testing

- **`model_test.go`, pure.** Construct a `Model`, send `tea.KeyMsg` and `app.Event` values, assert on the resulting state. No terminal, no timing, no sleeps. Covers focus cycling, `back()` order, every drill-down row of §4.1, one-watch-at-a-time cancellation, filtering, and error handling.
- **`golden_test.go`.** Render `View()` over `fake.Provider` data into `testdata/golden/*.txt`, regenerated with `-update` like `view`'s goldens and reviewed in the diff. Sizes: 80x24, 120x40 and 60x20; the last proves the layout degrades rather than panics.
- **`keys_test.go`.** Every binding appears in the help table and no key is bound twice in one context.
- **`TestTUIDependencyRule`.** The import guard.
- **`internal/cli/ui_test.go`.** The entry matrix of §2 through the existing in-process harness: TTY opens the UI, pipe prints help, `--no-tui` and `BAM_NO_TUI=1` print help, `bam ui` without a terminal exits 3.

No test sleeps and no test touches the network, exactly as in v0.1.

## 13. Part A acceptance criteria

1. `bam` on a terminal opens the UI; on a pipe it prints help; `--no-tui` and `BAM_NO_TUI=1` print help; `bam ui` without a terminal exits 3.
2. Plans, Builds and Presets load against the personal Bamboo, and `/` filters the focused list.
3. `enter` drills through every row of §4.1 and `esc` reverses each one.
4. Selecting a running build shows its stages and jobs advancing live, and selecting another build cancels the first watch.
5. Quitting the UI while a build runs leaves the build running.
6. `l` shows the failed jobs' logs of the selected build; `a` shows all jobs; `/` and `n` search inside them; `f` follows a running job.
7. `S`, `P` and `b` switch server, project and branch, and the panels reload.
8. `o` opens the selection in the browser; `y` reports a copy.
9. A Bamboo error surfaces in the status bar, `e` expands it, and the UI stays open.
10. `go test -race ./...` and `golangci-lint run` pass; `make docs` is not stale.

## 14. Out of scope for part A

- Triggering, cancelling and the variable form. Those are part B.
- Editing `.bam.yaml` from the UI.
- Mouse support.
- A run-sets panel. That follows the run-sets work in the PRD's Future section.
- Windows terminal support beyond what bubbletea gives for free; the release still builds windows/amd64.

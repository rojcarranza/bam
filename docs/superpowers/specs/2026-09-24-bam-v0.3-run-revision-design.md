# bam v0.3: `bam run --revision`

**Status:** Implemented | **Date:** 2026-09-24
**Product requirements:** [`docs/prd.md`](../../prd.md) "Then (v0.3)"
**Builds on:** [`2026-09-12-bam-cli-mvp-design.md`](2026-09-12-bam-cli-mvp-design.md) §7 (JSON contract), [`2026-09-22-bam-v0.3-run-edit-design.md`](2026-09-22-bam-v0.3-run-edit-design.md) (edit buffer header), [`2026-09-23-bam-v0.3-tui-home-design.md`](2026-09-23-bam-v0.3-tui-home-design.md) (run form, error overlay)

All hosts, keys, user names and revisions are placeholders.

## 1. Problem

`bam run` always builds the newest commit of the plan's default repository. Rolling back to a known commit, or rebuilding the commit an older build used, means opening the Bamboo web UI and using "Run customised".

`bam run --revision REV` triggers the build at the commit `REV`. The first use is an explicit SHA pasted from git; reusing the revision of a `--from` build is later work (section 11).

## 2. What Bamboo does

Learned with `go run ./tools/record -probe-run` against Bamboo 12.1.8 and recorded in `internal/provider/bamboo/testdata/recorded/`:

| Probe | Result | Recording |
| --- | --- | --- |
| `application.wadl`, build queue | `POST queue/{plan}` takes query parameters `stage`, `executeAllStages`, `customRevision` | `wadl_queue.txt` |
| `customRevision=<older full SHA>` | 200, `"triggerReason": "Custom revision build"`; the build builds that SHA and succeeds; its reason reads "Custom build by jdoe with revision SHA"; `onceOff: true` | `queue_revision.json`, `result_revision.json` |
| `customRevision=<7-character SHA>` | same as the full SHA; `vcsRevisionKey` is the full SHA | `queue_revision_short.json`, `result_revision_short.json` |
| `customRevision=0000…0000` (no such commit) | 200, `"triggerReason": "Custom revision build"`; the build settles as `lifeCycleState: NotBuilt`, `buildState: Unknown`, no start time, no revision | `queue_revision_invalid.json`, `result_revision_invalid.json` |
| verbose logs | no build queue parameter; only `POST queue/deployment` has `verboseLogging`. An unknown parameter on the build queue is ignored without error | `wadl_queue.txt` |

Consequences:

- bam cannot validate a revision before the trigger. Bamboo has no revision lookup over REST, and it accepts an unknown revision.
- A server that does not know `customRevision` would ignore it and build the newest commit. The trigger answer's `triggerReason` is the only signal that the revision was taken.
- `run --verbose` is out of scope (`docs/prd.md`).

## 3. Command

```
bam run <plan|target> --revision REV [--branch B] [--var k=v]... [--from N|last]
        [--edit] [--watch] [--timeout D] [--dry-run] [--json]
```

`--revision` is a flag on `bam build run` and therefore on its `bam run` shortcut. It combines with every existing flag.

- `REV` is passed to Bamboo exactly as given: full SHA, short SHA, or anything else. bam does no format check.
- Help text: `commit to build instead of the newest; Bamboo applies it to the plan's default repository`.
- `--branch`: the revision must exist on that branch's repository; Bamboo decides.
- `--from`: still reuses variables only.
- A plan with several repositories gets no special handling: Bamboo applies the revision to the default repository.
- Presets (targets) have no `revision` key. A pinned commit in a preset goes stale unnoticed; building an old commit is a decision made at run time.

## 4. Output

### 4.1 Text

`view.RunPlan` prints a `Revision` line after `Plan` when a revision is set, and nothing otherwise:

```
Plan     PROJ-PLAN
Revision abc1234
Vars     none
```

Without `--watch`, `view.Queued` replaces the watch hint with one that says when the revision is checked:

```
✓ Queued   PROJ-PLAN-12   http://bamboo.example.com/browse/PROJ-PLAN-12
  revision abc1234 is checked when the build starts: bam watch PROJ-PLAN-12
```

When a watched build with a revision ends as `not_built`, bam prints `Bamboo could not build revision abc1234` after the result line and its `next:` hints. The exit code stays 1 (a watched build that did not succeed).

### 4.2 `--edit`

The edit buffer's header names the revision when one is set:

```
# bam run PROJ-PLAN · default branch · revision abc1234 · server lab
```

The buffer body stays variables only. The revision is not editable in the buffer.

### 4.3 JSON

`RunDoc` (the `bam run --json` and `--dry-run --json` document) gains one field:

```json
{ "key": "PROJ-PLAN-12", "url": "…", "plan_key": "PROJ-PLAN", "branch": "", "revision": "abc1234", "variables": {} }
```

`revision` is `""` when no revision was given, as `branch` is. No existing field changes. The NDJSON watch events are unchanged; a `not_built` result is already in the `done` event's state.

## 5. Architecture

### 5.1 `provider`

`TriggerRequest` gains `Revision string`. Empty means the newest commit.

`provider/fake` records the request's revision in `Triggered`; `TriggerResult` and `TriggerErr` already let a test script any answer, so an ignored revision is set up directly with `TriggerErr` wrapping `errs.ErrUnsupported` (section 5.2), with no separate switch.

### 5.2 `provider/bamboo`

`Trigger` adds `customRevision=REV` to the queue query when `Revision` is set. Variables stay in the form body.

After a successful queue answer with `Revision` set, `Trigger` checks `triggerReason`. If it is not `Custom revision build`, it returns the queued build (key, URL, number) together with an error of kind bamboo that wraps `errs.ErrUnsupported`, What `Bamboo ignored the revision`. The string `Custom revision build` stays inside this package.

### 5.3 `app`

`PlanRef` gains `Revision string`, set by the caller from `--revision` or the form, never by `ResolvePlan`. It sits next to `Branch`, the other per-run choice of what to build, so `RunPlan`, `RunJSON` and the edit buffer read it without new parameters.

`Service.Run` passes `ref.Revision` in the `TriggerRequest`. When `Trigger` returns an error wrapping `errs.ErrUnsupported` together with a build key and `ref.Revision` is set:

1. Stop that build with `P.StopBuild`. A build that was just queued may have no job to stop yet, so retry on `s.Clock` every 2 seconds for up to 30 seconds while `StopBuild` answers not found.
2. Return an error of kind bamboo (exit 5), What `Bamboo ignored the revision; PROJ-PLAN-12 was stopped`, Why `this Bamboo does not support building a chosen revision over REST`, Try `run without --revision, or use Run customised in Bamboo`.
3. If stopping failed or timed out: What `Bamboo ignored the revision; PROJ-PLAN-12 is building the newest commit`, Try `bam build cancel PROJ-PLAN-12`.
4. The build is not recorded as this repository's last build in either case.

`app` still never prints; the messages travel as `*errs.Error`.

`EditBuffer`'s header line includes `revision REV` when `ref.Revision` is set.

### 5.4 `view`

- `RunPlan`: the `Revision` line (4.1).
- `Queued`: gains the revision hint (4.1). Its signature takes the revision.
- `RevisionNotBuilt(o, rev)`: the line after a `not_built` result (4.1).
- `RunJSON`: fills `revision` from `ref.Revision`.

### 5.5 `cli`

`--revision` on the run command. An explicit empty value (`--revision ""`) is a usage error, exit 2, `--revision needs a value`, checked before any configuration load or network call. The value is copied into `ref.Revision` after `ResolvePlan`. After a watch ends, `cli` calls `view.RevisionNotBuilt` when the final state is `not_built` and a revision was set.

## 6. Terminal UI

- The run form gets a **Revision** row below the variables, the last stop of the cursor. Existing cursor positions of the variables stay as they are. It is not a `formField`: it never mixes with variable values and never counts in "N of M changed". A plan with no variables still has this row, so the form's keys work on it.
- The row opens empty each time the form opens, shown as a dim `newest`. It is not filled from a preset or a previous build.
- `enter` edits it like a variable; `tab` and the cursor include it. No format check.
- `d` (dry run) shows a `revision REV` line under the plan line. (The form has no `$EDITOR` action; its `e` expands an error.)
- `ctrl-R` sets `ref.Revision` before calling `app.Run`.
- An ignored revision is a run error like any other: its What in the status bar, `e` for the Why and Try of section 5.3.
- When the watched build with a revision ends as `not_built`, the status bar reads `Bamboo could not build revision abc1234`; the home row takes the `not built` state as for any finished build.

## 7. Errors and exit codes

| Case | Exit | What / Try |
| --- | --- | --- |
| `--revision ""` | 2 | `--revision needs a value` |
| Bamboo ignored the revision, build stopped | 5 | `Bamboo ignored the revision; PROJ-PLAN-12 was stopped` / `run without --revision, or use Run customised in Bamboo` |
| Ignored, stop failed or timed out | 5 | `Bamboo ignored the revision; PROJ-PLAN-12 is building the newest commit` / `bam build cancel PROJ-PLAN-12` |
| Watched build with a revision ends `not_built` | 1 | the usual result and `next:` hints, then `Bamboo could not build revision abc1234` |
| Revision given, not watched | 0 | queued line with the revision hint |

## 8. Testing

Test first, per the plan. No test sleeps or touches the network.

- **`provider/bamboo`** (`httptest`): `customRevision` is in the query and not in the form body; no `customRevision` without a revision; `Custom revision build` passes; another reason returns the build and an error wrapping `ErrUnsupported`, using the existing `queue.json` fixture (`Manual build`) as the ignored answer. Hand-written fixtures `queue_revision.json`, `result_revision_not_built.json`; `TestRecorded*` checks them against the recordings of section 2, and that the invalid-revision result maps to `StateNotBuilt`.
- **`app`**: `Run` passes the revision; ignored revision stopped on the first try, on the third try (not found twice, fake clock), and never (timeout after 30 seconds of fake time); `--last` not written in any ignored case.
- **`cli`** (harness): `--revision` with `--dry-run` text and JSON; `revision` field `""` without the flag; queued hint without `--watch`; `not_built` watched build prints the line and exits 1; ignored revision exits 5 with the stopped message; `--revision ""` exits 2 without a network call; `--edit` header shows the revision.
- **`view`**: explicit expected strings for the `Revision` line, the queued hint and the not-built line; golden files only where a renderer changed.
- **TUI**: the Revision row (typing, `tab` order, empty on reopen), `ctrl-R` passes the revision, the overlay for an ignored revision, the status bar for `not_built`.
- **e2e** (`//go:build e2e`): with `-revision SHA`, run the plan at that revision, watch it, and check that `bam build show --json` reports the same SHA in `revisions`.
- **Recorder**: `-probe-run` stays; it re-records the fixtures of section 2.

## 10. Acceptance

Against the local Bamboo:

1. `bam run PLAN --revision <older SHA> --watch` builds that SHA; `bam build show` shows it under Revisions.
2. The same with the 7-character SHA.
3. `bam run PLAN --revision 0000000 --watch` ends `not built`, prints `Bamboo could not build revision 0000000`, exits 1.
4. `bam run PLAN --revision <SHA> --dry-run --json` shows `"revision"` and triggers nothing.
5. TUI: `R`, a revision in the form, `ctrl-R`: the build shows the revision in its detail.
6. `go test -race ./...`, `make lint`, `make check-fixtures`, `make docs` clean.

## 11. Out of scope

- Reusing a build's revision: done as `--revision from`, see [`2026-10-05-bam-run-revision-from-design.md`](2026-10-05-bam-run-revision-from-design.md).
- A `revision` key in presets.
- Choosing a revision per repository in multi-repository plans.
- Resolving tags or branch names to SHAs in bam.
- `run --verbose` (section 2).

# Bam v0.2 - Terminal UI, part B: run and cancel

**Status:** Implemented | **Date:** 2026-09-18
**Product requirements:** [`docs/prd.md`](../../prd.md) §7 "Next (v0.2): terminal UI"
**Builds on:** [`2026-09-18-bam-v0.2-tui-navigate-design.md`](2026-09-18-bam-v0.2-tui-navigate-design.md) (part A), [`2026-09-12-bam-cli-mvp-design.md`](2026-09-12-bam-cli-mvp-design.md)

This spec is the input to the v0.2 part B implementation plan. All hosts, keys and user names are placeholders.

## 1. Summary

Part A made the terminal UI read-only. Part B adds the mutating half: run a preset or a plan through a variable form prefilled from the preset and from a previous build, cancel a build, and preview what a run would send.

It adds no behaviour the commands lack. The same `app` use cases decide what is valid and what is sent, so `bam run` and the UI cannot disagree about a plan's variables.

Part B is the last piece of v0.2. v0.3 is the build-duration estimator.

## 2. What part B adds

| Key | Where | Does |
| --- | --- | --- |
| `R` | Plans, Builds, Presets, Main | open the run form for the selection |
| `C` | Builds, Main | cancel the selected build, after a confirmation |
| `p` | Builds, Main | save the selected build as a preset: asks for a name, then writes what `bam preset add NAME --from BUILD` writes and shows the file in the status bar |
| `enter` | form | start editing the field, or accept the edit |
| `tab`, `shift-tab` | form | next / previous field |
| `ctrl-R` | form | run |
| `d` | form | dry-run: show exactly what would be sent |
| `esc` | form | leave the field, then leave the form |
| `y`, `enter` / `n`, `esc` | confirmation | yes / no |

**No lowercase key mutates anything**, in part A or part B. `R` only opens a form, which changes nothing on the server. `ctrl-R` is the only key that triggers a build, and it cannot be struck while a field is being edited. `C` always asks first, naming the build key.

## 3. The one change to `app`

`app.ResolveVars` mixes two jobs: it fetches the plan's declared variables and a previous build's values, then applies the rules (`${ENV}` resolution, `required`, `options`, undeclared-name warnings). The form needs the rules on every keystroke and the fetch exactly once, so the two are separated.

```go
// VarBase fetches what the rules are applied to: a plan's declared variables
// and, when from is set, a previous build's values. It applies no rules.
func (s *Service) VarBase(ctx context.Context, ref PlanRef, from string) (VarSet, error)

// ValidateVars applies the rules to already-fetched values. It touches no
// network and no clock, so the UI may call it on every keystroke.
func ValidateVars(ref PlanRef, base VarSet, flags []string, getenv func(string) string) (VarSet, error)

// ResolveVars keeps its signature and its behaviour: VarBase, then
// ValidateVars.
func (s *Service) ResolveVars(ctx context.Context, ref PlanRef, o VarOptions) (VarSet, error)
```

`ResolveVars`'s existing v0.1 tests are not changed by this refactor. They passing unchanged is the evidence that the split was faithful; new tests cover `ValidateVars` directly.

`app` stays UI-ready: it still never prints, never reads stdin and never imports cobra, and `TestAppStaysUIReady` still enforces that.

Nothing else in `app` changes. `Run` and `Cancel` are used as they are.

## 4. The form

### 4.1 Layout

A fourth screen, `screenForm`, which takes the terminal the way the log screen does:

```
┏━Run provision-lab · PROJ-PROV12 · develop━━━━━━━━━━━━━━━━━━━━━━┓
┃                                                                ┃
┃▸ cluster_name    beta___________________  required             ┃
┃  cluster_type    k8s                      k8s | dcos           ┃
┃  region          eu-west-1                from #8              ┃
┃  ssh_key         ********                 env SSH_KEY (set)    ┃
┃  debug           false                    plan                 ┃
┃                                                                ┃
┃  4 of 5 changed from the plan's values                         ┃
┗━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━┛
 enter edit  tab next  ^R run  d dry-run  esc cancel
```

Three columns: the variable's name, its value, and its source or constraint. The header names the target, the plan or branch plan the run will go to, and the branch. The footer counts how many values differ from the plan's, because only those are sent.

### 4.2 State

```go
type formField struct {
	Name     string
	Value    string
	Source   string   // plan, target, from #8, env SSH_KEY, flag
	Secret   bool
	Required bool
	Options  []string // non-empty means a cycle widget, not free text
	Touched  bool     // an untouched secret field sends nothing
	Err      string   // from ValidateVars, shown against this field
}

type formState struct {
	ref     app.PlanRef
	target  string     // preset name; empty for a bare plan
	base    app.VarSet // fetched once, when the form opened
	fields  []formField
	cursor  int
	editing bool
	input   textinput.Model
	err     error // a form-level error that ctrl-R refuses on
}
```

### 4.3 Opening

`R` resolves the selection into a `PlanRef` with `app.ResolvePlan`: a preset resolves by its name, so its `branch`, `defaults`, `options` and `required` apply; a plan or a build resolves by its plan key, with no target. It then fetches `VarBase` once, with `from` set to the selected build when one is selected and to `last` otherwise, and builds the fields.

Fetching happens in a `tea.Cmd`, so the UI does not block; until it lands the form shows `loading`.

### 4.4 Editing and validation

`ValidateVars` runs on every change — an accepted edit, a cycled option — against the fields as `name=value` flags. Its error is a usage-kind `*errs.Error` naming a variable; the form shows it against that field and refuses `ctrl-R` while it stands. Warnings, such as an undeclared name, render dim and do not block, exactly as they do not block `bam run`.

An options field never accepts free text: `enter` and `space` step through the allowed values. That removes the commonest rejection before it can be typed.

Nothing is re-fetched while the form is open. `r` refetches `VarBase` when the plan may have changed.

### 4.5 Secrets

A field is secret when its name matches `password|secret|passphrase|sshkey`, when Bamboo returned `********` for it, or when its value resolved from a `${ENV}` reference.

- It renders `********` and its source. Its value is never shown, in the form, in the dry-run, in an error or in a log line.
- Editing accepts typing and echoes `********` per character.
- **An untouched secret field contributes nothing of its own**: the empty box on screen is never what is sent. Only a field the user typed into overrides the value underneath it.

What stands underneath it is whatever `bam run` would have used for the same preset — a plan value, a target default, or a `${ENV}` reference the target resolved. That is deliberate: `R` on `provision-lab` and `bam run provision-lab` must send the same variables, so the form may not silently drop a secret the preset configures. Dropping it would run the build with the wrong credentials, which is a worse failure than the one it would prevent.

The one value that is never sent back is the literal `********`. Bamboo returns it for a secret the API will not disclose, and returning it would overwrite the real secret with asterisks; `stripUntypedMasks` restores the plan's value instead. A `--from` build's masked value is skipped earlier, in `VarBase`, with a warning.

This is the same rule the rest of bam applies, including under `--debug` and in `--json`.

## 5. Running

`ctrl-R` runs `ValidateVars` once more, refuses on an error, then calls `app.Run` with `vs.Changed()` — the same set `bam run` sends, so a variable equal to the plan's value is not transmitted.

On success the form closes, the Builds panel reloads for that plan, the main panel opens the new build and a watch starts on it. That is the existing drill-into-a-build path, so part A's rule that **at most one watch runs** is inherited rather than re-implemented.

On failure the form stays open with the error in its footer. Nothing typed is lost.

`d` renders the exact `VarSet` the trigger would send, with secrets as `********`, in the overlay frame. It sends nothing and reaches no server.

## 6. Cancelling

`C` on a build opens a confirmation naming the build key. On yes, `app.Cancel` runs.

- `Cancel` already reports an already-finished build with a boolean rather than an error; that becomes a status-bar line, not an error overlay.
- The watch is left running. A cancelled build still transitions, and the watch reports the transition like any other.
- Nothing else cancels a build. Leaving the UI, leaving a screen and switching server all cancel *watches*, and a watch is not a build.

## 7. Errors

Unchanged from part A §6: an `*errs.Error`'s `What` goes to the status bar, `e` expands `Why` and `Try`, and the UI never exits on a use-case error. A rejected `ctrl-R` is not an error state, only a refusal: the message sits in the form footer and clears when the offending field changes.

## 8. Architecture

No new package and no new dependency. Part A's three charm modules cover the form: `textinput` for the edited field, and the existing overlay frame for the confirmation and the dry-run.

New files:

```
internal/view/tui/form.go        formState, field building, the form screen
internal/view/tui/confirm.go     the yes/no overlay
internal/app/vars.go             VarBase and ValidateVars (modified)
```

The dependency rule is unchanged: `view/tui` still imports only `provider`, `app`, `view`, `view/style` and `errs`, and `TestTUIDependencyRule` still enforces it.

## 9. Testing

- **Pure model tests** for building fields from a `VarSet`, cycling an options field, the validation feedback loop, the untouched-secret rule, `ctrl-R` refusing while an error stands, and `esc` leaving the field before leaving the form.
- **Goldens** for the form at 80x24 and for the confirmation overlay, regenerated with `-update` and read.
- **A secret test** that no rendered form, dry-run or status line contains a secret's value.
- **`app` tests** for `ValidateVars` directly, covering `${ENV}`, `required` and `options`. `ResolveVars`'s v0.1 tests stand unchanged.
- **A read-only test** that every key that reaches a provider mutation is `R`, `ctrl-R` or `C`, and that `ctrl-R` and `C` are unreachable without a confirmation or a form.

No test sleeps, no test touches the network, no test starts a real `tea.Program`.

## 10. Part B acceptance criteria

1. `R` on a preset opens a form with the preset's defaults, its allowed values and its required fields marked, prefilled from the previous build where the server allows it.
2. `R` on a plan or a build opens a form for that plan with no target rules.
3. An options field cycles and cannot take free text; a required field empty refuses `ctrl-R` and says which field.
4. An unset `${ENV}` reference refuses `ctrl-R` and names the environment variable.
5. A secret's value never appears on screen, in a dry-run or in an error.
6. `d` shows exactly what would be sent and reaches no server.
7. `ctrl-R` triggers, the new build opens in the main panel, and its watch starts; the previous watch is cancelled.
8. A failed trigger leaves the form open with everything typed still there.
9. `C` asks before cancelling, cancels on yes, and does nothing on no; an already-finished build is reported in the status bar, not as an error.
10. `go test -race ./...` and `golangci-lint run` pass; `make docs` is not stale.

## 11. Out of scope for part B

- `run --edit`, `run --revision` and `run --verbose`. Those are v0.3.
- Run sets, matrix expansion and `rerun --failed`. Those follow the PRD's Future section.
- Editing `.bam.yaml` from the UI, including `bam target add`'s job.
- Re-running a build with its own variables in one keystroke. The form prefilled from that build is how part B does it.
